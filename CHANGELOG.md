## 6.x (current)

### v6.44 - Fixes

- Fixed: after an import, the Issues search box was not cleared. The code cleared an element named searchIssues, but the box is named searchIssue, so a search term typed beforehand kept filtering the newly imported issues out of view - the exact symptom the surrounding code was written to prevent.
- Found by a new repository check that cross-references every getElementById target against the ids actually present in the markup. A wrong id fails silently in JavaScript, so nothing else would have caught it.

### v6.43 - Features

- Added Connect data file under Settings › Data. Your data is kept in a real file on disk and every change is written straight to it, so it no longer depends on browser storage working at all.
- This is the answer when a browser accepts saves and then discards them: there is nothing to fix in the save logic, because there is nowhere to save to. A file has none of those limits.
- The tracker reconnects to the file and reloads from it automatically when you open it. Where the browser will not remember the connection either, it takes one click to reconnect - rather than re-importing a JSON every time.
- Connecting to a file that already holds tracker data asks whether to load it or overwrite it, so pointing it at an existing export is a safe way to recover.
- A green file indicator appears next to the version number while auto-saving is active, and turns red if a write fails.
- Save & verify now confirms the file write as well, and treats the file as the copy that matters.
- Keep the file on OneDrive or a network drive and it is backed up as well.

### v6.42 - Features

- Added Save & verify under Settings › Data. It saves your data to this browser, forces the database write out immediately, then reads both copies back and counts the records to prove they were kept.
- It reports each store separately - browser storage and the local database - so a partial failure is visible rather than averaged into a single Saved message.
- The verdict is stated in the terms that matter: whether your data will still be there when you reopen the page. If it will not, it lists the usual causes and tells you to export a file first.
- The existing Save Data button has been renamed Export to file. It wrote a file to disk and never touched browser storage, so its name was the opposite of what it did - which is misleading when you are trying to work out why data is not being kept.
- Saving remains automatic after every change. This button is for checking that saving works, not something you need to press routinely.

### v6.41 - Fixes

- Fixed the cause of imported data vanishing when the tracker is closed and reopened: saves were assumed to have worked.
- A browser can accept a write and silently discard it - in a private window, with site data blocked, or on a page opened from a file. Nothing threw an error, so the app believed it had saved. Every save now reads the value back and confirms it actually stayed.
- The app now tests whether storage works when it starts, before you do any work, and shows a banner if it does not - rather than letting you work for an hour and lose it.
- After an import, the pending database write is flushed straight away instead of waiting for its delay, and the result says whether the data was saved or only loaded into the page.
- If an import cannot be persisted you now get an explicit, persistent warning that it will be gone when the page closes, instead of a success message.

### v6.40 - Features

- Importing now shows a preview first. An import is the most destructive action in the app, and it was previously committed on the strength of a filename alone.
- The preview shows when the file was saved and which version wrote it, counts of projects, issues, sub-tasks and clients, how many archived records it contains, and the first few records by name - so you can confirm it is the right file before agreeing.
- Where you already have data, Replace and Add alongside are now radio options that state the outcome of each, including how many records you would end up with either way.
- A file containing no projects or issues is called out and the Import button is disabled, rather than letting you run an import that does nothing.
- The file is only parsed and inspected at this stage; your data is untouched until you accept. Cancelling leaves everything exactly as it was.
- A missing saved-date is flagged, since that usually means a hand-edited or partial file.

### v6.39 - Fixes

- Fixed: importing into an empty tracker still asked "Replace current data? Click Cancel to merge instead" - a question with no meaningful answer when there is nothing to replace, which read like a warning that the import was about to destroy something.
- The question is now only asked when there is genuinely existing data to replace or merge with. An import into an empty tracker just proceeds.
- When it is asked, it now uses the app's own dialog rather than a raw browser prompt, states how many projects and issues are in the file and how many you already have, spells out what OK and Cancel each do, and notes that a snapshot is taken either way.

### v6.38 - Fixes

- Explains why a newly downloaded copy opens empty. The tracker is run straight from a file, and in some browsers - Firefox in particular - local files are scoped to their exact filename, so every differently named build gets its own separate storage. Chrome and Edge share storage across all local files; Safari blocks it outright.
- This is why 6.37 could not recover the data: it can only read storage it is allowed to see, and a different filename is a different store. The data is still intact with the file it was created in.
- An empty tracker opened from a file now says this plainly, instead of showing a neutral "No projects" message, and offers a direct Import link.
- The recommended pattern is to keep one filename and overwrite it when upgrading, so your storage follows the file.
- The storage panel now notes when the app is running from a file rather than a server.

### v6.37 - Fixes

- Fixed: a new version opened with an empty tracker, and importing a file appeared to do nothing.
- Two separate faults. First, saved data is written in two different shapes - save() stores the state object directly, while the database copy, the snapshots and the JSON export all wrap it as { savedAt, data }. Several readers only understood one shape and saw no projects in the other.
- Second, the import never brought the incoming records up to the current schema, and the imported settings replaced the status registry the app derives its status tables from. Rows then carried statuses and column views that could not be resolved, so the table rendered empty - exactly the symptom of an import that had done nothing.
- Imports now run through the same normalisation as a normal load, rebuild the status tables, and report how many projects and issues arrived.
- Start-up now looks for data saved under an earlier storage key. The key carries a schema number, so a build that bumps it starts reading an empty slot while the previous data sits untouched beside it. The most recent is adopted and re-saved; nothing is deleted.
- Importing now takes a snapshot first, clears any filter left over from before, and switches to the Projects page - the import is run from Settings, where the tables are hidden and so were not redrawn.
- Snapshot files can now be imported directly; previously only an exported JSON was accepted.

### v6.36 - Fixes

- The Kanban toolbar is now a single row at every width. It never wraps and it never clips.
- Rather than choosing between the two failure modes, the row is built so it can never want more width than it has: every element has a floor low enough that the total fits a narrow phone, and the squeeze is absorbed in a deliberate order.
- Give-way order: the heading strapline, then the heading, then the search box, then the filter dropdowns, and last the button labels - which collapse to a + and a cross, keeping a square tap target and carrying their meaning in a tooltip.
- Nothing is ever hidden or cut off: both buttons, both filters and the search box stay present and operable all the way down.
- Every element holding text now truncates with an ellipsis. Text is what makes a flex item refuse to shrink, and that was the underlying cause of the overflow in 6.34 and the wrapping before it.

### v6.29 - Performance

- Fixed the stutter when scrolling a long list. Four separate causes, none of which were the scrolling itself.
- Row hover was animated. Entering a row started a quarter-second background transition on every cell in it, so moving the pointer while scrolling had hundreds of elements animating at once. Hover is now an instant colour change; the drag handle and row buttons still fade, as they are one element each.
- The hover handler ran on every cell and span the pointer passed over, and each run searched the whole table twice to find the rows to highlight. It now remembers which group is highlighted and only touches the page when that changes.
- The routine that decides whether Description and Comments need a more link measured one cell, wrote to it, then measured the next - and reading a height after a write forces the browser to lay the entire table out again. On a 200-row table that was around 400 layouts in one pass. It now measures every cell together and writes afterwards, which is two layouts regardless of how many rows there are.
- Only the table you are looking at is rebuilt. Almost every interaction rebuilt Projects, Issues and the Kanban board together, so two thirds of that work was discarded immediately. Hidden tables are marked as needing a rebuild and built when you switch to them.
- The two measurement passes a single rebuild used to schedule are now one.
- The clamped description cells are given paint containment, so changing one no longer prompts the browser to re-examine its neighbours.
- Transitions are effectively switched off for anyone whose system asks for reduced motion.

### v6.18 - Features

- CSV import for projects and issues, in Settings > Data next to the export buttons. Drop the file in, or choose it; there is no need to open it.
- The columns are the ones the app already exports, so you can export, edit in Excel and bring the file straight back. Whether it holds projects or issues is worked out from the columns rather than asked for.
- Imports merge with what is already recorded rather than replacing it. Sub-task rows are re-nested under their parent, and priorities are renumbered so nothing collides.
- Rows that already exist are matched on client plus name, or client plus title for issues, ignoring case and spacing. They are listed before anything happens, and you choose whether to skip them, merge into the existing record, or add them as separate records.

- Nothing is written until you press Import, and a snapshot is taken first, so a whole import can be undone from Settings > Data.
- Status names are matched against your configured statuses, so a renamed status still imports. Anything unrecognised is reported and left at the default rather than silently dropped.

### v6.16 - Fixes

- Fixed: the Jira sync dialog printed raw escape codes instead of characters - the document icon showed as a backslash sequence, and a dash in the instructions did the same. Introduced in 6.15 when that dialog was added.
- Cause: those two strings were written as escape sequences into the HTML rather than into JavaScript. A browser decodes such sequences inside a script, but prints them literally in markup.
- Added a check that scans the markup for undecoded escape sequences, so this cannot ship again. The same fault appeared in 6.2 on several buttons; nothing was watching for it until now.

### v6.15 - Fixes

- You can now drop the Jira CSV straight onto the sync dialog, or choose it with a file picker. No opening the file, no copying, no pasting.
- Fixed a serious parsing fault found by testing against a real export. Jira wraps each Description in quotes, and those descriptions routinely contain hundreds of newlines - FIX messages, stack traces, pasted logs. The previous parser split on newlines before parsing, so 19 tickets arrived as 657 fragments.
- The result was not merely wrong, it was invented: it reported 33 tickets rather than 19, fourteen of them fabricated from image filenames inside the descriptions, such as image-20260615-071435.png being read as a ticket called IMAGE-20260615.
- Reading is now a proper CSV parse where quotes span newlines, and the issue key is taken only from the key column and only when the whole cell is a key. A byte-order mark at the start of the file no longer defeats the header detection.
- Dates like 30/Jul/26 10:08, BST are now understood; the trailing timezone abbreviation is dropped rather than breaking the date.
- Pasting still works and uses exactly the same parser, so there is only one path to trust.

### v6.14 - Features

- Jira status sync. Settings > Ticket links now builds a JQL query covering exactly the tickets linked in the tracker, opens it in Jira, and takes the results back by copy and paste.
- The synced status appears next to each Jira key on the Issues table, tinted green when the ticket looks finished. Hovering shows when it was last updated in Jira and when you last synced.
- Paste accepts a CSV export, a copied block from the issue navigator, or plain lines with a key on each. The delimiter and the columns are detected rather than assumed, and dates in Jira's own format are understood.
- A preview shows exactly what would change before anything is applied, including tickets that are not linked to anything here.
- Why paste rather than a live API call: Jira Cloud does not permit cross-origin requests from a page like this one, so the browser discards the response before the app can read it. Atlassian removed that allowlist from Cloud deliberately and expect calls to go through a server, which a single file cannot provide. Copy and paste needs no API token, so no credentials are stored or carried in your exports.
- Nothing was added to the Issues table itself: the status rides alongside the existing Jira cell, because the column manager hides columns by position and a new one would have shifted them all.

### v6.9 - Features

- Status categories are now configurable in Settings > Display. Add your own, rename any of them, and delete the ones you added.
- Each category carries behaviour flags rather than relying on its name: Terminal (counts as finished and drops out of live views), Counts complete (feeds the sub-task progress bars), Aggregate tile (the Pending bucket on Issues), and Row style (normal, strike through or dimmed).
- Because behaviour comes from the flags, renaming a category can no longer break row styling, sub-task progress or the Pending tile. Ten places that previously compared against the literal names done, dropped and waiting were rewritten.
- Added Status assignment, so any of the twelve statuses can be moved to a different category - for example putting Pending Build under Active so it stops counting as waiting.
- The Issues Pending tile and its Any Waiting filter option now follow whichever category holds the aggregate flag, and take its name.
- A category still holding a status cannot be deleted, and the fallback category is always kept, so every status resolves to something real.
- Added Reset to defaults, restoring the six original categories and assignments.
- Categories and assignments are stored in settings, so they travel with JSON export and import.

### v6.1 - Storage

- IndexedDB storage engine: your data is now held in the browser's local database, which is not bound by the roughly 5 MB localStorage quota.
- localStorage is kept as a fast start-up cache, so the app still opens instantly and nothing about start-up order changed.
- Snapshots moved out of localStorage into the database, releasing the quota they were competing with your live data for.
- Existing localStorage snapshots are migrated automatically on first open, and only removed once the database copy is confirmed.
- If the cache is cleared or blocked, the app now recovers your data from the database on the next open.
- A save failure is only reported when both stores fail, so a full cache no longer produces a false alarm.
- Storage failures no longer sacrifice your snapshots to make room.
- Settings > Data now shows which engine is active, the cache mirror size, and total site storage usage.
- Pending writes are flushed when the tab is hidden or closed, so the last edit cannot be lost.

- Terminal categories (Done, Dropped) now drive live/finished behaviour in one place instead of being repeated throughout the code.
- Unknown or legacy status values fall back to Active so they stay visible rather than silently disappearing from views.
- Added category-aware timing helpers, so KPIs measure time to or within a category rather than a single named status.
